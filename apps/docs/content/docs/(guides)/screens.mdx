---
title: Screens
description: Publish typed route context to TailorKit apps.
---

A screen connects a place in your host product to an app view. The basic flow
has three parts: define the screen, publish its context, and render the app.

TailorKit does not own your router or inspect the browser URL. Your route tells
TailorKit which screen is current.

## Define a screen

Add a stable path and its context to the server contract:

```ts title="src/lib/tailorkit.ts"
import { createTailorKit } from "tailorkit";
import { z } from "zod";

export const tailorKit = createTailorKit({
  components: {},
  screens: {
    "/customers": {
      context: z.object({
        customers: z.array(
          z.object({
            id: z.string(),
            name: z.string(),
          }),
        ),
      }),
    },
  },
});
```

## Publish the current screen

Call the hook in the client route that owns the data:

```tsx
function CustomersPage({ customers }) {
  tailor.useCurrentScreen({
    screen: "/customers",
    context: { customers },
  });

  return <CustomerList customers={customers} />;
}
```

The hook must be rendered below `tailor.Root`. Supplying `context` means the
screen is ready; no status is needed.

## Render an app

`AppView` uses the current screen automatically:

```tsx
<tailor.AppView app={app} />
```

That is the complete ready-state setup. The sections below cover unresolved
data, nested routes, and less common integrations.

## Loading and error states

Publish a status when the complete context is not available:

```tsx
function CustomersPage() {
  const query = useQuery({
    queryKey: ["customers"],
    queryFn: getCustomers,
  });

  tailor.useCurrentScreen(
    query.isPending
      ? { screen: "/customers", status: "loading" }
      : query.isError
        ? { screen: "/customers", status: "error" }
        : { screen: "/customers", context: { customers: query.data } },
  );

  return query.data ? <CustomerList customers={query.data} /> : null;
}
```

Loading and error states do not need context and cannot receive it. This keeps
stale or incomplete route data out of the app. An app may define matching
loading and error UI; otherwise it renders nothing until the context is ready.

## Nested screens

Screen paths form a hierarchy. If the current path is
`/pages/customers/detail`, TailorKit tries these paths for each app:

1. `/pages/customers/detail`
2. `/pages/customers`
3. `/pages`
4. `/`

The first path implemented by the app is used. The complete context from the
current nested screen is passed to it.

Every nested context must therefore include the context of its closest defined
parent. Extend the parent schema to make this clear:

```ts
const pagesContext = z.object({ user });
const customersContext = pagesContext.extend({
  customers: z.array(customer),
});
const detailContext = customersContext.extend({
  customer,
});

const screens = {
  "/pages": { context: pagesContext },
  "/pages/customers": { context: customersContext },
  "/pages/customers/detail": { context: detailContext },
};
```

TailorKit checks this relationship when the server contract is defined. A
nested route publishes only its own path and complete context; TailorKit derives
the parent paths. The rule is transitive, so a deeply nested context also
contains the context defined at `/` when a root screen exists.

## Layouts and nested routes

A parent layout can remain registered while a nested route is mounted:

```tsx
function PagesLayout({ user }) {
  tailor.useCurrentScreen({
    screen: "/pages",
    context: { user },
  });

  return <Outlet />;
}

function CustomerRoute({ customer, customers, user }) {
  tailor.useCurrentScreen({
    screen: "/pages/customers/detail",
    context: { user, customers, customer },
  });

  return <CustomerDetails customer={customer} />;
}
```

TailorKit chooses the deepest mounted path. When the nested route unmounts, the
layout becomes current again. Avoid mounting unrelated screens at the same
depth; the result is ambiguous and produces a development warning.

## Server Components

Hooks cannot run in a React Server Component. Load the data on the server and
pass its serializable context to a small Client Component:

```tsx title="customer-screen.tsx"
"use client";

export function CustomerScreen({ customers }) {
  tailor.useCurrentScreen({
    screen: "/customers",
    context: { customers },
  });

  return null;
}
```

Render this bridge from the Server Component. Client-routed applications can
call the hook directly in their route component.

## Override the current screen

Most views should use the current route registration. A view that is independent
of the route can provide its screen directly:

```tsx
<tailor.AppView app={app} screen="/customers" context={{ customers }} />
```

Explicit loading and error states use the same shape as the hook:

```tsx
<tailor.AppView app={app} screen="/customers" status="loading" />
```

## Load installed apps

Use `useApps()` to load the apps available to the current authenticated scope:

```tsx
const { data: apps, error, status } = tailor.useApps();
```

`getApps()` and `getApp(id)` return the current cached snapshot outside React.

`AppView` normally resolves the client from the app registry. A local or custom
app can provide its client path directly:

```tsx
<tailor.AppView
  app={{
    id: "todo",
    clientPath: "/tailorkit/todo/client.js",
  }}
/>
```

## Responsibility boundary

The host owns routing, data fetching, permissions, and the context exposed to
apps. TailorKit tracks mounted registrations, selects the deepest current path,
finds the closest screen each app implements, and passes it the complete
context.
