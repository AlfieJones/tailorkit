## `defineClient`

Register one screen map for each host viewport your app supports:

```tsx
import { defineClient } from "@tailorkit/app";

export default defineClient({
  viewports: {
    navbar: { screens: { "/": navigation } },
    panel: { screens: { "/users": generalTools, "/users/detail": detail } },
  },
});
```

Viewport names and their supported scope paths come from generated host bindings.
A globally declared scope can only be registered under viewports that list it. Screen keys
must match the path passed to `createScreen`. An omitted viewport is unsupported.
A `false` screen entry explicitly disables that scope and stops ancestor fallback.

## `createScreen`

```tsx
import { createScreen } from "@tailorkit/app";

const detail = createScreen("/users/detail", {
  component: UserTools,
  loading: LoadingTools,
  error: ContextError,
});

function UserTools() {
  const { workspaceId, user } = detail.useContext();
  return <UserActions user={user} />;
}
```

The hook returns the composed, typed context from the selected scope and its
ancestors. It is available only while the ready component renders. `loading`
and `error` are optional; omitted handlers render nothing.

Each viewport selects exactly one screen, searching the active scope followed
by ancestors. A detail screen replaces the general screen in the same viewport.
Other viewports resolve independently. Only the selected screen and its ancestors
contribute readiness; descendant failures cannot block a general screen.

Missing matches render nothing. Missing declared ancestor context produces an
error state. Neither loading nor error triggers fallback to another screen.

`path`, `component`, and `useContext` are members of the returned screen definition.
The client's `$meta` and `$runtime` properties are internal sandbox details.

See [Scopes, screens, and viewports](/docs/screens) for host integration.
